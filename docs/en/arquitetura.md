# Solution architecture

## Overview

AeroTrack follows the minimum structure required by the Module 6 final
project: data source, ingestion/treatment/quality pipeline, enrichment
rules, database, consolidation pipeline, indicators and dashboard.

```text
Data source (public CSV, UCI Air Quality)
  |
Ingestion and treatment pipeline (pl_01_ingestion_treatment.hpl)
  |
Classification rules (CO level, NO2 level, time of day)
  |
PostgreSQL database (leituras_qualidade_ar, leituras_rejeitadas)
  |
Consolidation pipeline (pl_02_indicator_consolidation.hpl)
  |
Indicators (resumo_diario_qualidade_ar, resumo_mensal_qualidade_ar)
  |
Dashboard (dashboard/index.html)
```

The two pipelines are not run manually in sequence: the workflow
`wf_air_quality_orchestration.hwf` orchestrates `pl_01`'s execution and,
only after it succeeds, runs `pl_02`.

## pl_01_ingestion_treatment

| Step | Hop transform | What it does |
| --- | --- | --- |
| Ingestion | `CSVInput` | Reads `data/raw/AirQualityUCI.csv` (`;` separator, `,` decimal) |
| Quality | `FilterRows` | Removes the fully empty rows the dataset export leaves at the end of the file |
| Treatment | `Formula` | Combines the original date and time columns into a single text |
| Treatment | `NullIf` | Converts the `-200` sentinel (missing reading) to null, for the 13 numeric fields |
| Treatment | `SelectValues` (select) | Renames the treated numeric fields and drops the auxiliary fields |
| Treatment | `SelectValues` (metadata) | Converts the date-time text into the Date type |
| Enrichment | `Calculator` | Derives year, month, day, hour, weekday (number) and the reference date |
| Enrichment | `ValueMapper` | Converts the weekday number into its full name |
| Enrichment | `NumberRange` (shift) | Classifies the hour into night, morning, afternoon or evening |
| Enrichment | `NumberRange` (CO) | Classifies `co_gt` into GOOD, MODERATE or CRITICAL |
| Enrichment | `NumberRange` (NO2) | Classifies `no2_gt` into GOOD, MODERATE or CRITICAL |
| Business rule | `Janino` | Computes whether a reading is valid (has at least one reference pollutant) and whether the condition is critical |
| Quality | `FilterRows` | Splits valid readings from readings with no reference pollutant |
| Database | `InsertUpdate` | Writes valid readings to `leituras_qualidade_ar`, keyed on `data_hora` |
| Database | `TableOutput` | Writes rejected readings to `leituras_rejeitadas` |

### Why the -200 value needs explicit treatment

The original dataset uses `-200` to flag a missing reading on any sensor.
Without treatment, that value would drastically skew averages and
indicators. The `NullIf` step converts that sentinel to null before any
aggregation, and Janino flags a row that ended up with no reference
pollutant at all (CO, NOx and NO2) so it can be split off the main flow.

### Analytical classification

The GOOD / MODERATE / CRITICAL bands for CO and NO2 do not follow an
external regulatory standard. They are an analytical classification defined
for this project, calculated from the dataset's real distribution (the
CRITICAL band represents roughly the top decile of each pollutant), so the
critical-hours indicator is informative rather than trivial.

## pl_02_indicator_consolidation

| Step | Hop transform | What it does |
| --- | --- | --- |
| Daily consolidation | `TableInput` | Aggregates `leituras_qualidade_ar` by `data_referencia` |
| Database | `InsertUpdate` | Writes the summary to `resumo_diario_qualidade_ar`, keyed on `data_referencia` |
| Monthly consolidation | `TableInput` | Aggregates `leituras_qualidade_ar` by `ano` and `mes` |
| Database | `InsertUpdate` | Writes the summary to `resumo_mensal_qualidade_ar`, keyed on `(ano, mes)` |

## Orchestration (wf_air_quality_orchestration)

```text
START -> Ingestion and treatment -> Indicator consolidation -> Process completed
```

The second hop is only followed if the ingestion pipeline finishes
successfully, which prevents indicators from ever being consolidated from
an incomplete load.

## Dashboard

The dashboard is a static HTML page (`dashboard/index.html`) that reads
`dashboard/data/indicadores.json`. That file is generated by
`scripts/export_dashboard.sh`, which queries the `vw_indicadores_gerais` and
`vw_ranking_piores_dias` views plus the summary tables directly in
PostgreSQL. The charting library (Chart.js) is vendored under
`dashboard/vendor`, so the presentation works without an internet
connection.

## Rerun safety and idempotency

The final project's required question is: what happens if the pipeline is
run again against the same source data? In AeroTrack:

- `leituras_qualidade_ar` has a `UNIQUE` constraint on `data_hora`, and the
  load uses `Insert/Update`: a new run updates existing records instead of
  duplicating them.
- `resumo_diario_qualidade_ar` and `resumo_mensal_qualidade_ar` follow the
  same logic, keyed on `data_referencia` and on `(ano, mes)`.
- `leituras_rejeitadas` is truncated and fully reloaded on every run, since
  it represents the log of the latest load, not an accumulating history.

This strategy was validated by running the workflow twice in a row against
the same source file and confirming the row count in
`leituras_qualidade_ar` stayed identical (see
[docs/en/evidencias-testes.md](evidencias-testes.md)).
